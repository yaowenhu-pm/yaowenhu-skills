# 产品 one-pager

让读者快速判断：产品为谁解决什么问题，为什么值得做，先验证什么，怎样算成功，现在做到了哪里，还有哪个决定没定。默认交付简洁、可编辑的一页产品方向稿。

## 取得输入并确定本轮目的

先读用户提供的原稿、访谈、会议结论、产品资料及相关证据，区分本轮是从零起草、评估还是更新。文件或链接无法读取时说明缺口，利用已有信息继续起草；不要声称读过未取得的内容。

从材料中确认读者、这份稿要支持的决定、产品阶段和本轮范围。只补问会改变产品方向或写入对象的关键缺口；其余缺口可以在稿内标为“待确认”，不要求所有资料齐全才动笔。用户指定的主题、格式、篇幅与已有授权优先。

参考稿提供的是结构与判断方法，不自动成为新产品的事实。不要迁入参考产品的名字、角色、数字、期限、访谈结论或内部进展。

## 九个主题的默认结构

默认采用标题、版本／更新日期和“主题｜当前表述”两列表格。每行只承担一个主题，核心判断先写，必要限定紧跟其后。可直接使用 [填写模板](references/one-pager-template.md)。

| 主题 | 要回答的问题与写法 |
| --- | --- |
| 使命 | 为什么值得长期做？写预期改善的结果，解释“质量”“效率”等抽象词的实际含义；不要把愿景当作短期验收指标。 |
| 用户与场景 | 谁在什么场景处理什么任务？区分使用者、验收／决策者与付费者（如适用）。先明确首个用户群和首项核心任务，其他人群或相邻业务只说明边界。 |
| 定位与价值 | 现有替代做法是什么，具体痛点是什么，本产品如何改善？用“用户任务 → 成果 → 后续用途”写价值，说明成果进入哪个决定或原流程；只有假设时明确标注，避免堆功能与竞争口号。 |
| 长期方向 | 验证成立后希望服务到哪里？把长期方向与首版范围分开，时间跨度依产品约束填写，不默认套用固定年限。 |
| 阶段目标 | 当前阶段先验证什么？写时间点或触发条件、验证对象、样本／交付、验收条件。尚未拍板的数量和期限标为“拟”或“待确认”，不借用参考稿的门槛。 |
| 成功标准 | 什么行为或结果才算有效，如何记录？区分尝试、完成、被采用和再次使用；产品能生成成果不等于用户愿意采用。指标应能对应实际证据与下一步决定。 |
| 产品与体验原则 | 哪些取舍指导设计？选少量与本产品相关、能判断对错的原则，如先完成核心任务、结果可检查可修改、关键决定由人确认、接续现有流程、每页突出主要操作；不要直接复制一套口号。 |
| 当前进展 | 截至什么时候，已经完成什么，证据是什么？写清原型、Demo、模拟结果、真实试用和上线的实际状态，并标注尚未验证的部分。 |
| 当前最大未决 | 现在最影响方向或下一步的决定是什么？优先写一个主问题，说明决定后将改变的范围或验证动作；有材料依据时写负责人／决策节点。 |

九个主题是方向稿的默认骨架。用户明确要求另一种一页纸时按其目的取舍，保留必要的用户、价值、验证和状态信息；不要为了填满表格而编造内容。

## 把目标写成可验证的条件

- 用户群和核心任务没有收敛时，把“选定用户群／首任务并取得基线”作为阶段目标，不同时承诺多个场景的验证成功。
- 质量标准应说明关键错误、缺口或不可接受的结果；效率对比应采用可比案例，包含人工复核、修改和返工。未测出基线时，不把未经论证的降本或提效比例写成硬门槛。
- 面向工作任务的产品，写清成果由谁确认、被用于哪个后续动作或回填到哪里。消费或其他产品按其实际用户行为定义有效使用，不强套机构采购流程。
- 明确试用、购买意愿、采购条件和实际付款的不同状态。只有材料支持时才写购买或商业验证已经成立。
- 每个关键目标应指向一个可观察结果及对应决定。长期收益、宏观使命或累计生成量不能单独证明当前核心价值。

## 起草、评估与更新

**起草：**先理清“用户与任务 → 价值假设 → 验证目标 → 成功标准 → 当前状态 → 未决决定”，再填其余主题。默认正文约 600—1000 个中文字，按信息密度调整；资料少时写得更短，不用空话补足。篇幅超出时优先删重复，详细流程、参数和研究论证放到相关文档链接。用户要求严格一页时按目标介质检查版面，不能靠缩小到难读字号凑页数。

**评估：**先给一句总体判断，再指出具体表述的问题、对产品决定的影响和建议。仅有评估请求时不擅自覆盖原稿；明确要求重写时直接交付修改稿。

**更新：**先读当前版本和新增证据，再局部修改受影响的行。保留用户手改、已确认判断与未变的内容；新材料推翻旧判断时同步调整目标、成功标准和最大未决。更新日期与“当前进展截至日期”分别标明，不能用今天的日期让旧进展看起来已重新核实。来源不足的旧结论保留其原有状态或标明待核验。

## 证据与交付

关键数字、已完成事项、用户反馈及外部事实附可核对来源；判断、计划和未知在对应语句中直接写清。缺失的负责人、期限、样本量和结论不得自行写成已确认事实。文末可放简短“依据”行，列出确实读取过的资料，不把内部核对过程塞进正文。

对外版本按已授权的公开范围使用材料，写作方法可以复用，私人信息与内部证据不能随模板自动带出。

默认按用户要求的载体交付。若未指定，直接给出可复制的正文；指定飞书或其他在线文档时，使用当前可用工具及相应技能核对目标、写入并回读。在 NAILFIT 环境有 `codex-for-feishu` 时复用它的身份与文档流程；缺少连接时保留草稿并说明所缺步骤。不要依赖私人脚本、固定账号、组织配置或本机路径。

交付前检查：

- 首个用户群、核心任务和价值假设是否一致，功能是否挤掉了方向判断。
- 阶段目标是否能按成功标准验收，数量、日期和比例是否有依据或明确为拟议。
- Demo、试用、采纳、再次使用、采购和付款是否保持真实状态。
- 当前进展是否有截止日期，最大的未决是否能推动下一步决定。
- 稿件是否易读、可编辑，来源是否可回查；在线交付是否确已写入并读回。

用 $one-pager-doc，根据这些资料写一页产品方向稿。

事实、假设与待定项分清楚，先给我正文。
```

用 $one-pager-doc，更新这个 one-pager。

写回原文档后回读，并给我链接与关键变化。
```
