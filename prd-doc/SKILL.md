# prd-doc · PRD 撰写

血统：文档结构继承 table-docs（三列大表 + 多列参数表不拆），生产管线与协作约定继承
research-doc（feishu_bigtable 引擎、写作红线、手改后只增量）。本 skill 只补 PRD 特有的部分。

## 一、两种 PRD 骨架（先判断写哪种）

**A. 功能模块型**（对齐 infiDive《需求逻辑详述》的格式）：每个功能模块固定六项——

| 项 | 内容要求 |
|---|---|
| 需求名称 | 一句话说清模块是什么，括号内给关键机制速览 |
| 业务流程 | 箭头串起主路径 + 旁路，标注依赖服务（🔵 = 待后端定义） |
| 原型图 | 留位，链接或截图 |
| 界面交互说明 | 逐元素编号 ①②③：文案、交互、数据来源、空值兜底，一个元素不落 |
| 数据埋点 | pv、uv 逐条列，每条埋点标注它喂给哪个指标 |
| 特殊场景 | 异常与降级逐条编号：弱网、超时、素材缺失、服务异常、防刷 |

**B. 规格定义型**（数值体系、经济系统、接口口径这类给后端的规格）：

概述与设计原则 → 名词与口径定义 → 规格主体（计分表 / 曲线表 / 联动规则）→
防刷与边界 → 展示与可见性 → 数据规格（事件字段、远程配置清单、埋点补充）→
调参与迭代机制 → 待拍板项 → 附录（调研依据链接、各模块 PRD 嵌入对照）。

两种可以混合：规格型 PRD 里单个交互场景按 A 的六项展开。

## 二、大表映射与附表规则

- 整篇一张「类型 | 事项 | 说明」大表：**类型 = 章**（一、概述 / 二、口径 / …），
  **事项 = 条目**，**说明 = 内容**。同章连续多行重复写类型名，建表后合并、左对齐。
- **多列参数表不拆**（table-docs 规则）：计分总表、逐级数值表、字段定义表这类天然多列的表，
  不硬塞进说明列——主表对应位置加一行锚点（说明写"见附表 A：行为计分总表"），
  附表统一放主表之后的附表区，按 附表 A / B / C 编号，用 `feishu.py append` 的
  markdown 表格转原生表能力产出（自动估算列宽）。
- 原型图、流程图按 research-doc 的 ⟨CHART⟩ 标记嵌单元格；数据文件用 ⟨FILES⟩ 嵌附件。

## 三、PRD 写作纪律（在 research-doc 写作红线之上追加）

1. **数值必须可实现**：给公式 + 逐级数表（如 XP(n)=10×n² 附 L1-L10 每级数字），
   禁止"适当增加""视情况而定"这类研发无法落地的表述。
2. **每个数值参数三件套**：默认值 ｜ 是否进远程配置 ｜ 生效层级（全局/角色/用户）。
3. **待定项统一 🔵 标记**：行内标 🔵，并在"待拍板项"组集中汇总（内容、建议方案、决策人、
   影响哪些模块）；拍板后回填正文并删除标记，不留悬空 🔵。
4. **指标 ↔ 埋点对账**：每个指标能指到依赖的埋点事件，每个事件能回答"谁用它做什么决策"
   （防 Metrics Theater）；对不上的进"待拍板项"。
5. **口径操作化**：首次、会话、误触、有效互动这类词必须给可执行定义
   （如：误触 = 面板唤起后 <1s 收起且无后续动作），不能只给名词。
6. **异常与降级必写**：每个模块的弱网、超时、素材缺失、服务异常、防刷场景逐条编号，
   写清降级后的用户体验，不写"报错提示"了事。
7. **沿用 research-doc 写作红线**：结论不说满、任何时候不用「」、去术语口语化、
   括号内不拆行、引用带真实可点链接、判断带客观依据。
8. **对外称呼规范**：文档内出现团队成员一律用昵称（毅哥、龙哥等），零全名。

## 四、生产管线

1. **前置输入确认**：上位 PRD / 会议结论 / 调研文档（research-doc 产出）三样链接备齐，
   缺哪样先补哪样；正文引用调研结论时挂链接，不复述论证过程。
2. **拟标题 + 目录，用户确认后动笔**：标题按 feishu skill 命名规范带
   `[产品]` 前缀 + 版本号（如 `[产品]infiDive_数值体系PRD_v1.0`）；新建前做去重检查。
3. **构建**：复制 `~/.claude/skills/research-doc/scripts/feishu_bigtable.py`，
   填 DOCID / ROWS / CHART_DIR / ATTACH 运行（引擎用法与坑位见 research-doc SKILL.md
   第七节，全部已内置，勿退步）。
4. **附表**：主表建完后用 `~/.claude/skills/feishu/scripts/feishu.py append` 按编号
   逐个追加多列参数表。
5. **自检**（见第五节）→ 交付链接。
6. **交付后**：用户手改过的文档只做增量修改，禁止清空重建（research-doc 协作约定）；
   用户说"我改了"就拉全文 diff，把改动规律沉淀回 memory 与本 skill。

## 五、交付前自检清单

- [ ] 每个数值有公式或逐级数表，无"适当/酌情"字样
- [ ] 每个参数带三件套（默认值/远程配置/生效层级）
- [ ] 行内 🔵 与"待拍板项"组一一对应，无悬空
- [ ] 指标 ↔ 埋点逐条对得上；埋点公共属性（user_id、session_id、来源渠道等）声明过
- [ ] 每模块有异常与降级场景
- [ ] 口径词（首次/会话/误触/有效互动）全部有可执行定义
- [ ] `**` 残留 0、「」0、链接可点、合并左对齐、附表编号连续
- [ ] 标题带 [产品] 前缀与版本号；对外称呼零全名

## 六、版本与评审闭环

- 初稿 v1.0 → 评审 → 结论回填后标题加"（评审后）"或升 v1.1，由用户定。
- 文档末尾固定"修订记录"组：日期 ｜ 版本 ｜ 改了什么 ｜ 依据（评审/会议/数据）。
- 评审回填时保留修正痕迹（原表述 + 修正标注），不抹掉重写——与 research-doc
  的修正处置流程一致。
