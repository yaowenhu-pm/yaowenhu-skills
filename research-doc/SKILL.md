# research-doc · 调研文档撰写

从方桃子账号研究（2026-07）全程沉淀。核心主张：**先立假设，再用数据打靶**——不罗列发现，
让每个数字都在回答一个明确的问题。产出为飞书"一张大表"文档，引擎脚本在 `scripts/feishu_bigtable.py`。

## 一、文档结构（固定骨架）

整篇一张大表，「类型｜事项｜说明」三列。类型分组依次为：

| 类型组 | 内容要求 |
|---|---|
| 摘要 | 研究对象一句话 → 核心命题 → 三个发现（带关键数字）→ 对业务的启发。末行加**数据截止日期** |
| 目录 | 思维导图式层级文本（全角空格缩进，`• / -` 两级），读者可直接编辑 |
| 引言 | 研究逻辑 · 核心命题 · 各假设速览（带结论强弱）· 样本 · 数据来源（含**采集时间**）· 三类内容区分 |
| H1..Hn（每个假设一组） | 假设陈述 → 数据论证（含图）→ 小结（成立/待验证 + 强弱） |
| 结论与产品启发 | 假设回验一览 → 对业务的具体启发（可操作拆解）→ 可验证实验 → 度量建议（**对照公司现行北极星指标做体检**：选型对不对、聚合方式的漏洞、阈值是否退化、缺不缺护栏） |
| 研究边界与不严谨处 | 每个假设的局限 + 样本口径 + 缺失数据，**集中在这里说一次** |
| 数字来源 | **报告里出现的每一类数字→出处/算法/脚本名**，一行一类（大盘直读/接口原样/统计规则/词频/引自外部文档要注明非本研究产出），形成"数字→算法→数据文件→原始页面"完整证据链 |
| 参考资料 | 研究对象/关键素材/工具代码的**真实可点链接** |
| 附录 | 数据文件（**CSV 作为附件嵌入单元格**）· 复核方式 · **分析脚本也作为附件嵌入**——文档完全自包含，拿到链接即可下载数据、审查规则、复跑计算 |
| 标题的答案 | 放在**最末尾**：一句话答案 → 分层数据支撑（带假设编号和强弱）→ 更深一层（标注"解读，非实测"）→ 对业务的收束。标题抛问题、正文摆数据、结尾给答案，闭环 |

假设数量收窄到 **3 条**为宜；每条标注结论强弱（强/中/弱），核心命题压成**一句话**。

**标题规范**：用"一个具体、能被数据回答、让人想知道答案的问句 + 副标题"，例：
"明知是AI，用户为什么还在喊'桃子早安'？——2295条评论里的关系数据与产品启发"。
不用大而空的问题；数据反差是常用的钩子之一，但问句不必刻意追求反直觉——具体和可回答比反直觉重要。
文档末尾必须有"标题的答案"组回答它。

## 二、立论与论证纪律（最高优先级——任何情况下不得出现严重错误）

**严谨是硬约束，不是风格偏好。** 立论和论证层面的错误会原样传导给读者并被当作事实使用
（实例：报告把不适错误归因为"恐怖谷"，读者随即以此理解数据，错误完成了复制）。
以下每条都来自一次真实翻车，写内容时逐条对照：

1. **先做指向分析，再贴机制标签。** 看到现象先问"它指向什么对象"，逐条读原文归类，
   然后才允许套理论词。现成理论词（恐怖谷/网络效应/飞轮…）是模式匹配陷阱——它让论证
   显得有学理，但机制可能根本对不上。（实例：不适实际指向"AI 开号过日常"的越界行为，
   而非角色拟真度；"恐怖谷"贴错了。）
2. **过于工整的结论句是危险信号。** "引力与斥力同源"这类对仗句有叙事美感，但现实机制
   很少这么对称——写出漂亮对仗的那一刻，回头查一遍证据。
3. **n=1 归纳不得写成验证结论。** 没有对照组就没有"必要性"；"数据上看""数据证明"这类
   措辞只能用于真的有数据支撑的比较。（实例："缺四要素的角色数据上看不具备留人能力"——
   根本没有其他角色的数据。）
4. **修正错误时，新结论的确定性不得超过新证据的等级。** 改错的时刻是最容易再次说满的
   时刻（实例：修正"恐怖谷"后立刻写出"拟真可以做足"，又被打回）。替换表述先自问：
   新证据支持到哪一级，就说到哪一级。
5. **归一化选择会驱动结论，必须多口径检验。** 比值指标（如每千赞评论数）换个分母结论
   可能反转；报告比值时必须同时报绝对量，并说明口径选择的理由。
6. **主动检验混杂变量，尤其是时间。** 类型对比前先看同类型内部随时间的变化（实例：
   正片自身评赞比一个月内翻倍，而对比组全发布在后期——"2.5 倍"被时间污染）。
7. **类间对比必须做分项稳健性检验。** 类平均可能被单条驱动（实例："随拍 27% 讨论真假"
   实为 ggez 单条 49% 拉动，其余两条只有 12-16%）。
8. **定义性结果不当行为洞察。** （实例：剧集催更率高于日常——日常本来就没有"下一集"
   可催，这是定义差异不是用户行为发现。）
9. **对抗性审查是交付前的内置环节，不是读者的工作。** 初稿完成后，用"哪条证据能证伪它"
   逐条攻击自己的假设；把不确定性写进"研究边界"不等于处理了它——边界一节不是免责声明。

**交付后仍发现错误的处置流程**：
① 出"修正说明"，错误（结论/机制写错）与不够严谨（强度/口径过头）分开列，先只发布错误项；
② 文档**保留修正痕迹**——原表述+修正标注+文末"修订记录"组，不抹掉重写（修正过程本身是
方法论可信度的证据）；③ 同步群消息（简短、写明错在哪、限定条件）；④ 构建脚本加禁重建
护栏，防止旧版本回退覆盖修正。

## 三、写作红线（用户逐字改出来的偏好，必须遵守）

1. **结论不说满**：单因素归因一律降格——"留下的原因**之一**是…"而不是"留下的**是**…"；"要回答的问题**之一**"。
2. **命题句只放命题**：核心命题的单元格只留命题本身，解释性展开放论证部分。
3. **不反复自贬**：结论处写"强（强佐证）"即可，"非铁证/待验证"等限定**只在"研究边界"一节集中说一次**。
4. **任何时候不使用「」**，用 "" 引号。
5. **去术语、口语化**："A/B 测…测好感度与留存"→"两种话术哪种更好？"。
6. **删重复背景**：摘要说过的信息，正文不再整句复述。
7. **判断必须带客观依据**：说"制作省事"要补时长/图文比例；说"高赞"要给赞数。
8. **引用必须可溯源**：评论/引文逐条带来源链接；每条数据发现能在数据文件里复核。
9. **区分三类内容并显式标注**：①实测数据（可复核）②机械统计（规则公开）③解读与假设（主观判断）。
10. **数据时效**：写明采集日期与时段，注明"数字为采集时刻快照"；复采一次证明数字在自然增长（活数据自证）。

## 四、排版规则（引擎已内置，写内容时用标记）

- `**加粗**` 标记关键数字与结论词（引擎解析为真加粗，状态跨行延续不残留星号）
- 句号/分号后**自动另起一行**；序号 ①②③ 前另起一行；冒号后若是多点列举（同段含分号）另起一行
- **括号内不拆行**（括号是整体）
- `[文字](url)` 生成真实可点链接
- 类型列每组只写一次（合并后不重复），**左对齐**（不居中）
- 说明列图表格式：`⟨CHART⟩图名.png|图注文字`；附件格式：`⟨FILES⟩说明文字`
- 组间空行由读者手动加——**重建会丢空行**，见第六节协作约定

## 五、数据与图表规范

- **CSV 列序**：视频/条目 ID · URL · **文案 · 类型**（紧跟 URL 右边）· 时间 · 各指标。让人打开就知道每行是什么。
- 图表用 matplotlib 生成 PNG（中文字体 `Arial Unicode MS`/`Hiragino Sans GB`），一个假设配一张核心图，克制配色（灰#B7C0D8 做对比项、蓝#2E5BFF 做主项、橙#FF7A45 做警示项），数值直接标在柱上。
- 无法拿到的指标（如他人账号播放量）用代理指标并显式说明（如"每千赞评论数"）。

## 六、协作约定（重要）

- **构建脚本是初稿真源，用户手改后文档为真源**：用户在飞书手动改过之后，一律只做**增量修改**
  （改单格、插块、replace_file），**禁止清空重建**（会覆盖用户改动和手动空行）。
- 用户手改后：拉全文与快照 diff（改前先存快照 JSON），逐处分析改动意图，把规律沉淀进
  memory（`feedback_report_writing_style`）和本 skill。
- 无法主动感知用户改动（没有事件订阅），需要用户说"我改了"再去 diff。

## 七、飞书 API 引擎与坑（scripts/feishu_bigtable.py 已全部内置）

依赖 `~/.claude/skills/feishu` 的授权（`scripts/feishu.py` 的 token）。引擎用法见脚本头部注释：
改 `DOCID` 和 `ROWS` 内容后运行即可产出完整文档。

踩过的坑（引擎已处理，改引擎时别退步）：

| 坑 | 处置 |
|---|---|
| 建表 API 单表 ≥10 行报 1770001 | 走 **descendant 接口**一次建整表（实测 42 行×3 列 350+ 块 OK） |
| descendant 报 1770041 schema mismatch 极难定位 | 十有八九是某个 cell 的 **children 为空数组**——空格也要放一个空格文本块 |
| 单元格嵌图 | descendant 里放**空图块** `image:{}` → 建完按"type27 且无 token"找到真实 id → 上传 `parent_type=docx_image, parent_node=图块id` → PATCH `replace_image` |
| 单元格嵌文件附件 | descendant 里放 file 块直接报 1770030；要**建完表后** POST `/blocks/{cell}/children` 插空 file 块 |
| replace_file 报 1770025 | 必须带 `params={document_revision_id:-1}`；且创建后要 **sleep 几秒 + 重新 GET 全量块**再回填（飞书异步包 view 容器） |
| 合并单元格后对齐丢失 | 合并（`merge_table_cells`，end 索引不含）会重置对齐，**合并后重新 PATCH 对齐**，注意加节流防频控 |
| 文件块读回来 parent 不是 cell | 飞书自动包了一层 view 块(type33)，属正常，校验时看 view 的 parent |
| append/create 命令 | 不读文件路径、不渲染行内 md——大表/嵌图/链接一律走 descendant 自建 |
| **给已有表格增量加行**（用户手改后禁重建时的扩表法） | PATCH 表块 `insert_table_row{row_index:N}`=在第 N 行位置插入空行（原 N 行下移）；插完 **重新 GET** 拿新 cells → 向 cell POST children 填内容 → 删 cell 原空块 → merge 新组 → **补左对齐** → 目录格里补对应条目 |
| 频控（连续 PATCH 返回非 JSON） | 循环 PATCH 时每次 sleep 0.15s，失败重试 2-3 次 |

## 八、执行清单（新调研从零到交付）

1. 数据采集（方式因对象而异）→ 原始数据落 CSV/JSON，**每条带可溯源 ID/链接**；CSV 列序：ID · URL · **文案 · 类型**（紧跟 URL 右边）· 时间 · 指标
2. 机械统计脚本（规则公开可复现）→ 跑出关键数字
3. 与用户讨论定**核心命题（一句话）+ 3 条假设**，确认后再动笔；取标题（问句式，见第一节标题规范），给 4-6 个候选让用户选
4. 生成图表 PNG（每假设一张）
5. 复制 `scripts/feishu_bigtable.py`，填 ROWS 内容（遵守二、三、四节规则），运行产出
6. **对抗性审查（交付前必做）**：逐条攻击自己的假设——指向分析做了吗？混杂变量（时间/人群/归一化口径）查了吗？类间对比做过单条驱动检验吗？有没有 n=1 写成结论、对仗句没验证、定义性结果冒充洞察？（详见第二节）
7. 自检：`**`残留=0、「」=0、图/附件（数据+脚本）齐、链接可点、合并左对齐、含采集时间、有"数字来源"组、末尾有"标题的答案"组
8. 交付后用户手改 → diff 分析（改前先存全文快照 JSON）→ 沉淀偏好回 memory 与本 skill → 此后只增量修改
